El Puerto

Un servidor Linux sin servicios es un muelle vacío: tiene estructura, pero nadie entra ni sale. Esta unidad trata de lo que hace que un servidor sirva para algo.

La idea en un minuto

Vamos a imaginar que su servidor Fedora es un puerto marítimo, como los del Canal de Panamá. Un puerto recibe barcos, descarga mercancía, controla horarios, asigna muelles y decide quién puede entrar. Un servidor hace exactamente eso, pero con paquetes de datos en lugar de contenedores.

La analogía tiene un buen chiste escondido: en inglés y en redes se usa la misma palabra. Cada servicio atiende en un puerto (un número, como el 22 o el 80) y ese número funciona como el muelle al que debe llegar cada barco. Si el barco llega al muelle equivocado, nadie lo atiende.

Reglas del puerto

1. Cada servicio es un oficio del puerto con una tarea concreta.
2. Cada oficio trabaja en un muelle (número de puerto).
3. Todo lo que se deja abierto es una puerta por la que alguien puede entrar. Por eso cada tema termina con una ficha de seguridad.

3.1.1 · Muelle 22

SSHd: el práctico del puerto

Cuando un barco grande llega a un puerto desconocido, sube a bordo un práctico: alguien autorizado que conoce las aguas y guía la maniobra. SSH cumple ese papel: permite que un administrador suba a su servidor desde cualquier lugar, con identidad verificada y sin que nadie vea lo que ocurre a bordo.

Teoría

SSH (Secure Shell) es un protocolo que da acceso remoto a la terminal de otra máquina a través de un canal cifrado. sshd es el servicio (daemon) que corre en el servidor y espera conexiones en el puerto 22/TCP. El comando ssh es el cliente.

Antes existía Telnet, que hacía lo mismo pero enviaba todo en texto plano, usuario y contraseña incluidos. Cualquiera que estuviera mirando la red veía las credenciales. SSH nació para resolver exactamente eso.

Dato clave

SSH no solo cifra el contenido: también verifica que el servidor es quien dice ser, usando una llave pública que el cliente guarda en ~/.ssh/known_hosts la primera vez que se conecta.

Comandos de este tema

Estos son todos los comandos que van a usar hoy. Léanlos antes de la práctica. Toque cada uno para ver qué hace y un ejemplo.

systemctl status sshd

Función: muestra si el servicio está activo, desde cuándo y sus últimos mensajes. Es lo primero que se revisa cuando algo no responde.

$ systemctl status sshd
● sshd.service - OpenSSH server daemon
     Active: active (running) since ...

Busque la línea Active:. Si dice inactive o failed, el servicio no está atendiendo.

sudo dnf install openssh-server -y

Función: instala el paquete que contiene el servicio sshd. La opción -y responde "sí" automáticamente a la confirmación.

$ sudo dnf install openssh-server -y
Nothing to do. (si ya estaba instalado)

Ya lo vieron en la Unidad 1 (instalación de paquetes). Aquí se aplica a un servicio.

sudo systemctl enable --now sshd

Función: hace dos cosas a la vez. enable lo configura para arrancar en cada inicio del sistema y --now lo inicia en este momento.

$ sudo systemctl enable --now sshd

Sin enable, el servicio funciona hoy pero desaparece al reiniciar. Sin --now, queda programado pero no arranca hasta el próximo reinicio.

ip -br addr

Función: lista las interfaces de red con su dirección IP en formato breve. Necesitan la IP del servidor para conectarse a él.

$ ip -br addr
lo      UNKNOWN  127.0.0.1/8
ens160  UP       192.168.1.50/24

Ignoren lo (es la interfaz interna). La IP que sirve es la de la interfaz en estado UP, aquí 192.168.1.50.

ssh usuario@IP_DEL_SERVIDOR

Función: abre una sesión remota en el servidor como el usuario indicado. Se ejecuta desde la máquina cliente.

$ ssh maria@192.168.1.50
The authenticity of host '192.168.1.50' can't be established.
Are you sure you want to continue connecting (yes/no)? yes
maria@192.168.1.50's password:

Ese mensaje es el paso 2 de la animación: el servidor presenta su llave y usted decide si confía. Solo aparece la primera vez.

sudo sshd -T

Función: muestra la configuración efectiva de sshd, es decir, lo que el servicio realmente está usando después de leer todos los archivos. Se filtra con grep.

$ sudo sshd -T | grep -i permitrootlogin
permitrootlogin no

Úsenlo para comprobar un cambio. En Fedora, sshd_config también lee archivos de /etc/ssh/sshd_config.d/, y cuando una opción aparece repetida gana la primera que se lee. Por eso lo que usted escribió y lo que está activo pueden diferir.

sudo sshd -t

Función: revisa que la sintaxis del archivo de configuración sea válida, sin reiniciar nada. Si no imprime nada, todo está bien.

$ sudo sshd -t
(sin salida = configuración válida)

Hábito de administrador: nunca reinicie sshd sin validar. Un error de sintaxis puede dejarlo sin acceso remoto a su propio servidor.

sudo systemctl restart sshd

Función: detiene y vuelve a iniciar el servicio para que lea la configuración nueva.

$ sudo systemctl restart sshd

Las sesiones SSH ya abiertas normalmente no se cierran; las nuevas usan la configuración actualizada.

sudo firewall-cmd --list-services

Función: muestra qué servicios deja pasar el firewall. Para entrar por SSH, ssh debe estar en la lista.

$ sudo firewall-cmd --list-services
cockpit dhcpv6-client ssh
sudo journalctl -u sshd

Función: muestra el registro (log) del servicio: quién entró, quién falló y cuándo. Es la herramienta de auditoría básica.

$ sudo journalctl -u sshd -n 5
Accepted password for maria from 192.168.1.20 port 51234 ssh2
Failed password for invalid user admin from 203.0.113.9 port 40022 ssh2

Los "Failed password" repetidos desde una misma IP son la huella de un intento de fuerza bruta.
